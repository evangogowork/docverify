# docverify 面试题

这些问题都按「面试官真的会这么问」来写。每题先给一句话答案，再展开，最后是追问。
答案都落在这个仓库的代码和实测数据上。源码位置用相对路径加 `@learn` 锚点名，在教学模式页面里点「看源码」，能直接跳到固定在某个 commit 上的 GitHub 行号。

> 关于数字：简历上那段经历里的数字（每天三万多份、错误自动通过降低四成二、自动匹配率从七成一到八成六）是在公司生产环境里的结果，**不是这个仓库测出来的**。这个仓库只报告它自己跑出来的数：评测集、混沌测试、对照组。面试时两类数字要分开说。

## 项目概述

### 讲讲这个项目？（一分钟版）

**一句话答案：** 一个文档验证工作流的后端：平台交上营业执照这类材料，系统抽出字段、和账户记录比对、该自动的自动、该人审的人审，再用签名回调把结果通知回平台，重复消息、杀进程、超时都不会让一个 case 被处理两次。

**展开：**
- 链路是 API → S3 → S3 触发的 Lambda → SQS FIFO（按账户分组）→ worker → DynamoDB / MySQL → 回调发件箱 → 平台。全部在本地 LocalStack 上真跑，Lambda 是真的 Lambda 容器。
- 状态在 DynamoDB，每次转移都是条件写，同一次写里追加 history；MySQL 存审计投影、账户、回调发件箱；Redis 存去重 key。
- 决策的原则只有一条：不确定的 AI 输出不能单独决定账户状态。只有全部检查通过、匹配过线才自动通过；只有高置信度读出的确定性规则失败才自动驳回；其他进人审。
- 正确性用混沌测试证明：五个 worker、随机 SIGKILL、重放重复消息、一部分抽取慢过可见性超时，断言每一步只提交一次、每份文档都得到正确结论。每层保护都有一个开关，关掉以后对应的测试会变红。
- 还有一套评测集当 CI 的发布门禁，按失败类别和名字来源分组报告。

**追问：** 你在里面最难的一块是什么？
答：让测试真的能失败。第一版混沌测试只断言「到了终态」，关掉条件写也是绿的。查数据库才发现很多 case 是进了死信，也算终态。改成断言每份都 APPROVED、再加一个「锁中途过期」的确定性场景之后，关掉条件写才会红。见 `docs/tutorial/06-idempotency.md`。

### 这个项目和你简历上那段经历是什么关系？

**一句话答案：** 简历上是我在公司做的生产系统；这个仓库是我用开源组件把同样的设计从零重写一遍，让别人能跑、能读、能验证，但数字只报告仓库自己测出来的。

**展开：**
- 设计是一一对应的：阶段拆分、版本化 API 加异步回调、按账户分区的 FIFO、条件写的状态机、Redis 去重、MySQL 审计、最小堆路由、按类别的评测集门禁。
- 不一样的地方：AWS 换成 LocalStack；模型换成本地 Tesseract 加规则，留了可替换的抽取器接口；数据是脚本生成的合成文档。
- 所以仓库里不会出现「每天三万份」这种数字。仓库里能说的是：评测集一百四十七份文档上零错误自动通过、混沌测试的对照组结果这些。

**追问：** 那简历上的「错误自动通过降低四成二」你怎么证明？
答：那是公司里上线前后的对比，基线是老流程。我能讲清楚它是怎么来的：引入置信度阈值和「确定性规则才能自动驳回、全部通过才能自动通过」以后，原来会被模型直接放行的低置信度 case 改走人审。仓库里的对应物是 `decide.py` 的策略和评测集的 `incorrect_auto_approvals` 一列，但仓库的数字是在合成数据上测的，不能拿来替简历背书。

## 设计取舍

### 为什么状态放 DynamoDB，审计却放 MySQL？

**一句话答案：** 状态需要「按 key 的原子条件写」，DynamoDB 正好擅长；审计需要按时间、actor、原因做关系查询，MySQL 擅长。

**展开：**
- 状态机的核心是 `ConditionExpression: state = :from AND round = :round`（`docverify/states.py`，锚点 `transition`）。单条 item 上的条件写不需要锁，也不需要事务。
- 两个库之间没有分布式事务，所以权威记录放在 DynamoDB：同一次条件写里往 item 的 `history` 追加一条，带唯一 `write_id`。
- MySQL 的 `audit_log` 是投影，`write_id` 唯一，`reconcile()` 能把崩溃窗口里漏掉的行补上，补多少次都只有一行。

**追问：** 为什么不全放 MySQL，用一个事务搞定？
答：可以，规模小的时候甚至更简单。选 DynamoDB 是因为 case 状态的访问模式就是「按 case_id 读写」，并且要水平扩展；条件写在这个模式下最便宜。代价就是跨库一致性要自己做，这里用的是「权威记录 + 投影 + 对账」。

### 为什么用 SQS FIFO，而且按账户分组？

**一句话答案：** 同一个账户的材料必须按顺序处理，不同账户之间要并行；FIFO 的 MessageGroupId 正好是这个语义。

**展开：**
- `lambdas/intake/handler.py`（锚点 `lambda-intake`）里 `MessageGroupId = account_id`。
- 同一组里，前一条没确认，后一条不会投出来。所以一个账户连交两份材料，不会出现旧结论盖掉新结论。
- worker 可以随便加，组越多并行度越高。
- `MessageDeduplicationId = case_id-r轮次`，SQS 自己在五分钟窗口里丢掉重复发送。

**追问：** FIFO 有吞吐上限，热点账户怎么办？
答：一个组内是串行的，所以单个账户的吞吐就是一个 worker 的吞吐。对文档验证来说这是对的取舍，一个商家不会一秒交一百份执照。整个队列的上限靠「组足够多」来摊开；真到上限，可以按账户哈希拆成多个队列。

### Redis 去重和 DynamoDB 条件写，不是重复了吗？

**一句话答案：** 不重复。Redis 是省力层，让重复的工作根本不发生；条件写是正确性层，保证就算重复的工作发生了，也只有一次能提交。

**展开：**
- Redis 有两个 key：`done:{case}:{轮次}` 表示这一轮做完了，副本直接丢；`lock:{case}:{轮次}` 是带 TTL 的处理锁，并发副本退让（`docverify/dedup.py`，锚点 `dedup`）。
- 锁只是租约。worker 停顿超过 TTL（GC、网络卡住），锁就没了，第二个 worker 会真的同时做同一步。
- 对照组实测：只关条件写，「锁中途过期」那个场景就会重复提交；只关 Redis，状态还是对的，但同一份文档会跑两次 OCR。

**追问：** 那为什么不用更强的分布式锁，比如 Redlock？
答：锁再强也有租约过期的问题，持锁的进程不知道自己的锁已经没了。正确的做法是 fencing：写入的时候带上一个版本，存储端拒绝旧的。这里的条件写就是 fencing，`state = :from` 起的就是 fencing token 的作用。

### 为什么文件先建 case、后放 S3？

**一句话答案：** S3 一落地就会触发 Lambda，如果先放文件，Lambda 可能在 case 还不存在的时候就跑起来。

**展开：**
- `docverify/api/main.py` 的 `create_case`（锚点 `upload`）先 `states.create`，再 `put_object`。
- 反过来的话要么 Lambda 失败重试，要么得在 Lambda 里处理「case 不存在」。
- 先建 case 的代价：如果放 S3 失败，会留下一条没有文件的 UPLOADED case。清扫任务会把它重新触发一次，Lambda 拿不到对象会失败，最后进 FAILED，有审计可查。

**追问：** 能不能做成原子的？
答：跨 DynamoDB 和 S3 做不了原子。能做的是让每一步都可以重试、并且有终点：要么走完，要么在审计里留下为什么没走完。

### 为什么自己实现编辑距离和 token-set，不用 rapidfuzz？

**一句话答案：** 为了让匹配逻辑完全可见、可测，而且别名索引和后缀处理这些关键规则是业务逻辑，不是库能给的。

**展开：**
- `docverify/match.py`（锚点 `normalize`、`similarity`、`alias-index`）。
- 用 hypothesis 钉住了度量的性质：编辑距离对称、有上下界、满足三角不等式；token-set 不在乎词序和重复。
- 生产环境用 rapidfuzz 更快，接口一样，换掉只要改两个函数。

**追问：** 归一化里最容易出错的是什么？
答：法律后缀。第一版别名索引把后缀也去掉了，结果「Acme Widgets Inc」以满分命中了「Acme Widgets LLC」，这两个是不同的法律实体。修法是把规范化之后的后缀集合也放进别名索引的 key。

### 为什么回调要走发件箱（outbox），而不是状态一变就直接 POST？

**一句话答案：** 直接 POST 的话，POST 失败或者进程在 POST 前死掉，这条通知就丢了；写进发件箱以后，投递变成一个可以重试、可以观察的后台任务。

**展开：**
- `callback_outbox` 唯一键是 `(case, 轮次, 状态)`，同一次转移被重放也只有一行。
- 分发器用 `FOR UPDATE SKIP LOCKED` 取行，开几个都不会抢同一行（`docverify/callbacks.py`，锚点 `dispatch`）。
- 失败按指数退避加抖动重试，六次失败标成 dead。每一次尝试的状态码和签名都记在 `callback_attempts`。

**追问：** 发件箱和状态写不在一个库里，还是会丢吧？
答：会有窗口：DynamoDB 提交了、发件箱还没写进程就死了。和审计一样，DynamoDB 的 history 是权威，可以从 history 重建发件箱。这个仓库现在只对审计做了 reconcile，发件箱的对账写在了「上生产还缺什么」里。

### 签名为什么要带时间戳？

**一句话答案：** 防重放：没有时间戳，一个合法签名的请求被截获以后可以永远重放。

**展开：**
- 头是 `t=<秒>,v1=<HMAC-SHA256(secret, "t." + body)>`，时间戳是签名内容的一部分，改不了（`docverify/callbacks.py`，锚点 `sign`）。
- 接收端拒绝五分钟以前的签名；比较用 `hmac.compare_digest`。
- 每次重试 event id 不变，平台按它去重。测试里断言了三次投递 event id 相同、每次签名都能验过。

**追问：** secret 怎么轮换？
答：现在是 `PUT /v1/webhooks` 重新注册就换一个。生产上要支持一段时间内两个 secret 同时有效，头里带多个 `v1=`，平台验过任意一个就行。

## 正确性和故障

### 同一条消息投递两次会怎样？

**一句话答案：** 第二次要么被 Redis 的 done 标记直接丢掉，要么在条件写那一步拿到 Conflict，不会提交第二次。

**展开：**
- 第一道：FIFO 同组串行，副本排在原消息后面，轮到它时这一轮通常已经做完。
- 第二道：worker 先查 `done:{case}:{轮次}`，在就直接确认删除，结果记为 `dedup:done`。教学模式里有个按钮「再投递一条重复消息」，能亲眼看到这一行。
- 第三道：就算前两道都没挡住，worker 读到的状态和库里的不一样，条件写失败，返回 `conflict`，不在别人的结果上再提交。

**追问：** 你怎么知道真的只提交了一次？
答：数审计表。`write_id` 每次成功的写都不同，所以重复提交一定会表现为两行。混沌测试按 `(case, 轮次, from, to)` 分组，断言每组只有一行。

### worker 处理到一半被 kill -9 会怎样？

**一句话答案：** 消息没被确认，可见性超时以后会投给别的 worker，它从 case 当前的状态接着做，已经提交的步骤不会重做。

**展开：**
- `process()` 是一个循环：按当前状态找下一步，做完提交，再看下一步（`docverify/worker.py`，锚点 `worker-process`）。
- 死在提交之前：这一步重做一次，OCR 多跑一次，这是唯一的浪费。
- 死在提交之后、写审计之前：history 已经有了，`reconcile()` 补审计。
- 死在全部做完、设置 done 标记之前：下一个 worker 读到状态已经结束，直接确认。

**追问：** 被杀的 worker 手里的锁呢？
答：锁有 TTL，最多挡三十秒。这也是一个取舍：TTL 太短会出现「锁中途过期」导致并发，TTL 太长会让崩溃后的重试变慢。正确性不依赖 TTL 选得对，因为有条件写兜底。

### 消息一直处理失败会怎样？

**一句话答案：** 有界重试：每次失败按指数退避推迟可见时间，收满 `maxReceiveCount` 次以后 SQS 把它移进死信队列，worker 把 case 标成 FAILED，原因写进审计。

**展开：**
- `_retry_later` 用 `ChangeMessageVisibility` 做退避，有上限（`DOCVERIFY_RETRY_CAP`）。
- 死信消费在 `drain_dlq`（锚点 `dlq`）。
- 测试用一张坏 PNG，断言它被收了 `maxReceiveCount` 次、最后 FAILED、审计原因是 `dead-letter: retries exhausted`。

**追问：** 我在测试里发现过一个和重试有关的真 bug，你猜是什么？
答：worker 一次预取十条消息、再一条条串行处理。慢的时候，排在后面的消息在本地等着就超过了可见性超时，被重投给别人；worker 被杀时，手里十条全都白白消耗一次投递次数，好好的文档也会进死信。改成每次只取一条（`DOCVERIFY_RECEIVE_BATCH`），混沌测试里的「进死信」才消失。

### S3 事件丢了怎么办？

**一句话答案：** 清扫任务每隔几秒扫一次，UPLOADED 超过三十秒的 case 重新调用一次 intake Lambda。

**展开：**
- 这是真碰到过的：bootstrap 重新部署 Lambda 时，LocalStack 换运行容器，这期间到达的 S3 事件丢了，case 永远停在 UPLOADED。
- 修了两处：代码哈希没变就不重新部署；加清扫任务（锚点 `sweeper`）。
- 清扫用 Redis `SET NX EX` 做成单例，多个 worker 只有一个在扫。重新调用是安全的，因为 Lambda 本身是幂等的。

**追问：** 扫全表不贵吗？
答：贵。这里是 Scan，适合演示规模。生产上应该在 `state` 上建 GSI，只查 UPLOADED 的，或者用 DynamoDB Streams 加一个延迟检查。

### 两个审核员同时点「领取」会怎样？

**一句话答案：** 堆里弹出以后还要做一次条件写占住 case，条件不成立就弹下一个，所以不会有一个 case 被发给两个人。

**展开：**
- 条件：`state = IN_REVIEW 并且（没人领 或 领取已过期）`（`docverify/api/main.py`，锚点 `claim`）。
- 提交结论时再加条件 `claimed_by = 我`，别人领的 case 你下不了结论，返回 409。
- 测试让十二个线程同时领，断言发出去的 case 没有重复。

**追问：** 审核员领了不审，走了怎么办？
答：领取有十五分钟的过期时间，过期以后刷新任务会把它放回堆里，别人可以再领。

## 扩展

### 流量放大十倍，先撞到哪里？

**一句话答案：** 先撞的是 OCR 的 CPU 和人审的人力，不是存储。

**展开：**
- worker 是无状态的，按队列深度横向扩就行；FIFO 组足够多时并行度够用。
- DynamoDB 按 case_id 打散，按需计费没有热点问题。
- MySQL 的审计写入是每次转移一行，十倍也就是每秒几十行到几百行，一个实例够。
- 真正的瓶颈是两个：OCR 或模型推理的算力，和进人审的那部分需要的人。后者靠提高自动化率来降，但不能放宽规则，所以要改的是抽取质量。

**追问：** 一百倍呢？
答：几件事要改：审核队列现在是单个 API 进程里的内存堆，多实例时要换成共享的（Redis 有序集合，或者按 key 分片的堆）；清扫和刷新从 Scan 换成 GSI 或 Streams；回调分发器按平台拆开，一个平台挂了不拖慢别的平台。

### 审核队列放在 API 进程的内存里，多开几个 API 实例怎么办？

**一句话答案：** 现在不行，这是有意的简化；但正确性不受影响，因为领取靠的是 DynamoDB 条件写，不是堆。

**展开：**
- 每个实例的堆都是从 DynamoDB 刷新出来的，最坏情况是两个实例弹出同一个 case，条件写让其中一个失败，它弹下一个。
- 损失的是排序的全局性：不同实例看到的「下一个」可能不一样。
- 要全局排序，key 公式不用变，换成 Redis 有序集合：score 就是 `enqueued_at − risk × 60`，ZPOPMIN 拿最小的。

**追问：** 为什么不一开始就用 Redis 有序集合？
答：简历上那条写的是最小堆，我想把「key 不随时间变」这个推导讲清楚；换成有序集合只是存储位置变了，公式一样。

### 一个热点账户一次交了一千份材料怎么办？

**一句话答案：** 它们在同一个 FIFO 组里串行处理，不会拖慢别的账户，但这个账户自己会慢。

**展开：**
- 这是按账户分组的直接后果，也是想要的效果：一个账户不能占满所有 worker。
- 如果业务上一个账户的多份材料之间其实互不依赖，可以把组 id 改成 `account_id + 材料类型`，让它们并行。
- 前提是确认「旧结论盖掉新结论」在新的分组下不会发生。

**追问：** 怎么发现有热点？
答：看每个 message group 的积压。SQS 本身不按组给指标，要在 worker 里按组打点，或者在入队时按账户计数。

## 测试

### 你怎么证明它是对的？

**一句话答案：** 三类测试：并发和混沌测试证明「只提交一次」，属性测试证明「策略永远不会在有失败项时自动通过」，评测集证明「在难的输入上也不乱下结论」，而且每一类都证明过自己能失败。

**展开：**
- 混沌：`tests/test_step06_chaos.py`（锚点 `test-chaos`）。
- 并发下结论：二十个线程同时下结论，只有一个成功（锚点 `test-concurrent-decisions`）。
- 策略属性测试：hypothesis 生成五百组随机的检查结果和匹配分数（锚点 `test-policy`）。
- 评测集门禁：`evals/run.py`（锚点 `eval-gate`），CI 每次跑。
- 前端：Playwright 从界面点通四条流程，包括教学模式和这页面试题。

**追问：** 测试全绿能说明什么？
答：只能说明在测到的场景里没出错。所以我更看重的是对照组：把保护关掉以后测试会不会红。如果关掉也是绿的，说明测试根本没测到。

### 那个「能失败的对照」是怎么设计的？

**一句话答案：** 每层保护都有一个只给测试用的开关，`scripts/failure_controls.sh` 依次关掉它们，跑同一组测试，看哪些变红。

**展开：**
- 开关是 `DOCVERIFY_UNSAFE_NO_CONDITIONAL_WRITES` 和 `DOCVERIFY_UNSAFE_NO_DEDUP`（`docverify/config.py`）。
- 实测结果见 `docs/tutorial/06-idempotency.md` 里的矩阵。
- 脚本每一轮先让 Python 打印它实际看到的开关值。这是踩坑踩出来的：第一次用 zsh 跑，`env $flags` 没有分词，「两个都关」实际上一个都没关，结果全绿。

**追问：** 「锁中途过期」那个测试为什么要先断言「确实出现了并发副本」？
答：因为它要证明的是「并发发生时也只提交一次」。如果这次运行碰巧没有发生并发，测试会空过。先断言场景是活的，再断言结果。

### 评测集是怎么组织的？

**一句话答案：** 十二个账户乘以五类输入，一共一百四十七份文档，每份都有「可接受的结论集合」，按类别报准确率和错误自动通过数，按名字来源报自动通过率。

**展开：**
- 五类：干净的、图像质量差的（模糊、噪点、低分辨率、旋转）、被篡改的（校验位、过期、名字不对、地址不对）、格式不支持的、名字有地区和文字差异的。
- 门禁在 `evals/thresholds.json`：错误自动通过必须是零；每类准确率有下限；名字分组之间的自动通过率差距有上限。
- 质量差的图「正确」的结论是人审或要求重新提交，不能是自动通过。

**追问：** 第一次跑门禁过了吗？
答：没过。干净的扫描件里，带 é 和 ø 的名字被英文 OCR 模型读错或者置信度很低，西班牙语名字和北欧名字的自动通过率只有三分之二，分组差距超过上限。修法不是调低阈值（那等于放宽规则），而是加上 Tesseract 的拉丁文字模型，再补上 ø、æ、ß 的转写。见 `docs/tutorial/10-evaluation.md`。

## 系统设计延伸

### 上生产还缺什么？

**一句话答案：** 缺的主要是运维和安全的部分：观测、密钥管理、多实例的审核队列、发件箱对账、数据保留。

**展开：**
- 观测：每个阶段的耗时直方图、队列积压、死信数、人审等待时间。现在只有日志。
- 密钥：JWT secret 和 webhook secret 现在从环境变量读，生产要放 KMS 或 Secrets Manager；webhook secret 至少要加密存储。
- 审核队列换成共享存储；清扫和刷新从 Scan 换成 GSI。
- 发件箱从 DynamoDB history 对账。
- 文档里有个人信息：S3 要加密、设生命周期，审计里不要存原文。

**追问：** 如果只能先做一件呢？
答：观测。没有阶段耗时和积压，扩容和排障都是瞎猜。

### 换成真实的 AWS，要改什么？

**一句话答案：** 代码基本不用改，改的是部署：去掉 `AWS_ENDPOINT_URL`，用 IaC 建资源，Lambda 换成真正的打包和 IAM 角色。

**展开：**
- boto3 客户端只认 `AWS_ENDPOINT_URL`，不设就连真 AWS（`docverify/aws.py`）。
- `bootstrap.py` 是演示用的，生产要换成 Terraform 或 CDK。
- Lambda 现在通过 compose 网络直连 MySQL 写审计；真 AWS 上要放进 VPC，或者改成只写 DynamoDB、审计交给 worker 或 Streams 去写。
- IAM 最小权限：API 只能写自己的桶前缀和表，Lambda 只能读桶、写表、发队列。

**追问：** Lambda 连 MySQL 有什么问题？
答：连接数。并发的 Lambda 每个都开连接，容易打满。要么加 RDS Proxy，要么让 Lambda 不碰 MySQL。

### 把 OCR 换成真模型（比如一个视觉大模型），要改什么？

**一句话答案：** 写一个实现 `Extractor` 接口的类，设 `DOCVERIFY_EXTRACTOR` 指过去，其余不用动；但要认真处理它的置信度。

**展开：**
- 接口在 `docverify/extract.py`（锚点 `extractor-protocol`），只要求返回带置信度的字段。
- 难点在置信度：很多模型不给校准过的置信度。要么用 logprob，要么用自一致性（多次采样看是否一致），要么在评测集上做校准。
- 换模型以后先跑评测集门禁，看错误自动通过是不是还是零、名字分组差距有没有变大。

**追问：** 模型直接给出「通过 / 不通过」不是更省事吗？
答：省事，但违反了这个系统唯一的原则。模型只负责读字段；结论由确定性规则和阈值决定，不确定的交给人。这样出了问题能解释是哪条规则、哪个字段。

## 简历对应

### 简历上写「每个阶段有明确的 API 契约」，面试官会怎么追问？

**一句话答案：** 会问「契约具体是什么、版本怎么演进」，我用仓库里的 `/v1` 接口和回调格式来回答。

**展开：**
- 提交：`POST /v1/cases`（multipart：account_id、doc_type、file），返回 case_id 和状态。
- 查询：`GET /v1/cases/{id}`、`/audit`、`/callbacks`；重新提交：`POST /v1/cases/{id}/resubmit`。
- 回调：`type`、`api_version`、`case_id`、`status`、`reasons`、`event_id`，加签名头。
- 每个阶段之间的「契约」是状态转移表本身：一个阶段只能把 case 从它负责的状态推到下一个状态。

**追问：** 要加一个字段，怎么不破坏四个平台？
答：只加不删、可选字段；破坏性改动走 `/v2`，`/v1` 保留到四个平台都迁走。回调里带 `api_version`，平台知道自己收到的是哪一版。

### 简历上写「自动匹配率从七成一提到八成六、没有放宽拒绝规则」，怎么用这个仓库讲？

**一句话答案：** 讲机制，不讲那两个数：仓库里同一份评测集上，朴素的精确匹配和完整的匹配器各跑一遍，自动通过率的差别是实测出来的，而拒绝规则一条都没改。

**展开：**
- `python -m evals.run --matcher exact` 跑朴素基线，`python -m evals.run` 跑完整匹配器。
- 两次的拒绝规则完全一样（`decide.py` 不变），变的只是名字匹配。
- 仓库实测：MATCH_RATE_PLACEHOLDER
- 简历上的七成一到八成六是生产数据上的结果，分布和这里的合成数据不一样，不能直接比。

**追问：** 自动通过率提高了，错误自动通过有没有跟着涨？
答：评测集同时报两列。仓库里完整匹配器的错误自动通过是零；门禁要求它必须是零，涨了 CI 就红。

### 简历上写「SQS FIFO 按账户分区、幂等消费者、有界重试、死信队列」，会被怎么追问？

**一句话答案：** 一般会追问「怎么证明重复和重启不会处理两次」，我用混沌测试和对照组矩阵回答。

**展开：**
- 分区：`MessageGroupId = account_id`；有序性测试断言同一账户五份材料的抽取顺序和入队顺序一致。
- 幂等：done 标记 + 处理锁 + 条件写三层，各自的作用用对照组证明。
- 有界重试和死信：毒消息测试。
- 我还会主动说那个预取十条的 bug：这是「幂等」和「重试次数」之间一个不明显的交互。

**追问：** 你们生产上用的是 SQS 自带的去重，为什么还要自己做？
答：SQS FIFO 的去重窗口只有五分钟，而且只按 MessageDeduplicationId。一个小时以后的重放、或者内容相同但 id 不同的重复，它都挡不住。

### 简历上写「最小堆按风险分和等待时间排序」，会被怎么追问？

**一句话答案：** 一般会追问「等待时间每秒都在变，堆怎么维护」，答案是 key 可以在入队时算一次。

**展开：**
- 优先级 `risk × K + (now − t)`，所有 case 的 now 一样，所以顺序等价于 `t − risk × K` 从小到大。
- 堆的 key 不随时间变，不需要重排（`docverify/review.py`，锚点 `review-heap`）。
- K 是「一分风险值多少秒等待」，这里是六十秒；它是一个业务旋钮。

**追问：** K 怎么定？
答：看两件事：高风险 case 的最长等待时间，和低风险 case 的最长等待时间，各有一个服务目标，K 在两者之间取。仓库里有一个测试专门钉住「低风险的老 case 能超过高风险的新 case」这个边界。
